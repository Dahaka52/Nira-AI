# Chat GPT
По текущей архитектуре Ниры уже можно строить нормальный эмоциональный слой. Но я бы не добавляла эмоции прямо внутрь `Nira` и не заставляла LLM самой решать «сейчас я злая на 0.73». Это быстро превратится в кашу из промптов, тегов и случайных скачков характера.

Главная идея, которую я бы заложила сейчас:

> **LLM не является источником эмоционального состояния. LLM получает текущее состояние Ниры и эмоциональную оценку события; отдельный Emotion Engine хранит, изменяет и затухает это состояние.**

Это довольно хорошо совпадает с тем, куда сейчас движутся исследования эмоциональных агентов: continuous PAD/state representation, appraisal, отдельная эмоциональная память и разные скорости изменения состояния. Например, опубликованный в 2026 Sentipolis прямо использует непрерывный PAD, dual-speed dynamics и coupling эмоций с памятью; другая работа 2026 года показывает, что appraisal через ожидания и их нарушение лучше моделирует эмоциональные переходы, чем простое присваивание статического emotion label. ([ACL Anthology][1])

## 1. Что у Ниры уже хорошо, а где архитектурная проблема

По документу транспортная часть у тебя уже довольно взрослая: event-driven pipeline, отдельные операции STT/T2T/TTS, streaming, preemption, barge-in, Discord bridge, memory layers. 

Но для настоящего эмоционального поведения сейчас есть несколько дыр.

### 1.1. У Ниры вообще нет постоянного emotional state

Есть:

* character;
* personality;
* beliefs;
* episodic/semantic/working memory;
* known users;
* история диалога.

Но нет объекта вроде:

```text
EmotionalState
SocialState
MoodState
Appraisal
```

То есть сейчас Нира может **говорить эмоциональными словами**, но у неё нет механизма:

> «Мне было неприятно → я запомнила это → сейчас этот человек снова пришёл → ещё до его новой фразы я отношусь к нему настороженно».

А именно это и даст ощущение живого персонажа.

Текущая memory-архитектура уже хорошо подходит как фундамент: episodic, semantic, working memory, retrieval, consolidation и personality/identity. 

Но эмоциональные признаки в эту систему пока не встроены.

---

### 1.2. `known_users.json` — это идентификация, а не социальная модель

Сейчас:

```text
Discord ID
имя
display name
aliases
```

Этого хватает для:

> «Это Вова».

Но недостаточно для:

> «Это Вова, я ему доверяю, он обычно шутит, я расслабляюсь рядом с ним».

Тебе нужен отдельный `SocialMemory` / `RelationshipModel`.

Например:

```yaml
person_id: user_123

familiarity: 0.94
trust: 0.91
affection: 0.83
respect: 0.76
fear: 0.00
irritation: 0.12
dependency: 0.41

interaction_count: 842
last_interaction: ...
recent_emotional_events: ...
```

Причём это **не должно быть статическим personality profile**.

Это состояние, которое меняется после событий.

---

### 1.3. У тебя memory пока больше «хранит информацию», чем влияет на эмоции

Например, память может вернуть:

> Вова любит X.

Но должна возвращать также:

> Это событие связано с положительной эмоциональной оценкой +0.6.

То есть воспоминание должно содержать примерно:

```json
{
  "content": "Вова однажды помог Нире разобраться...",
  "importance": 0.82,
  "emotional_valence": 0.71,
  "arousal": 0.43,
  "social_target": "vova",
  "emotion": "gratitude",
  "confidence": 0.91
}
```

Тогда retrieval сможет вернуть не просто факт, а **эмоционально окрашенный эпизод**.

---

## 2. Самое важное: не строй систему только из 6–8 эмоций

Вот здесь есть важный архитектурный нюанс.

Я бы **не делала внутреннее состояние Ниры дискретным**:

```text
happy
sad
angry
fear
...
```

Это удобно для TTS, но плохо для моделирования живого состояния.

Лучше использовать **трёхслойную модель**.

### Слой A — непрерывное состояние

PAD:

```text
Pleasure   -1 ... +1
Arousal    -1 ... +1
Dominance  -1 ... +1
```

То есть:

```text
P = насколько приятно/неприятно
A = насколько возбуждённо/спокойно
D = насколько контролирую ситуацию
```

Это уже используется в современных архитектурах эмоциональных агентов. Sentipolis, например, строится именно вокруг continuous PAD + динамики состояния + emotion-memory coupling. ([ACL Anthology][1])

---

### Слой B — дискретные эмоции

Я бы для Ниры стартовала с:

```text
neutral
joy
sadness
anger
fear
disgust
surprise
interest
```

А затем добавила социальные:

```text
affection
trust
embarrassment
guilt
shame
pride
gratitude
contempt
```

Причём последние не обязательно должны быть фундаментальными физиологическими состояниями. Это **высокоуровневые социальные эмоции**, которые очень полезны именно для VTuber.

Например:

```text
PAD:
P +0.72
A +0.38
D +0.21

Primary emotion:
affection 0.68

Secondary:
joy 0.44
trust 0.79
```

И это уже гораздо интереснее, чем:

```text
happy = true
```

---

### Слой C — mood

Вот это особенно важно.

Не путай:

**emotion**

и

**mood**.

Эмоция:

> Вова сказал что-то очень смешное → +joy.

Mood:

> последние два часа происходило много хорошего → Нира в целом находится в хорошем расположении духа.

Поэтому:

```text
Emotion:
joy = 0.72

Mood:
positive_bias = +0.31
energy = +0.18
stress = 0.12
```

Эмоция меняется быстро.

Mood — медленно.

Именно это создаёт ощущение непрерывности личности.

# 3. Я бы построила Emotion Engine вот так

Целевой pipeline:

```text

                      │
              ┌───────▼────────┐
              │   PERCEPTION   │
              │ STT / text /   │
              │ speaker / scene│
              └───────┬────────┘
                      │
                      ▼

              │   для Ниры?"   │

          ▼           ▼            ▼
       goals      person       memories
          │           │            │
          └───────────┼────────────┘
                      ▼
              ┌────────────────┐
              │ EMOTION ENGINE │
              │ PAD + emotions │
              │ mood + stress  │
              └───────┬────────┘
                      │

                     │

```

И самое главное: **Emotion Engine работает до генерации ответа**, а не после.

# 4. Appraisal — это сердце всей системы

Это, пожалуй, самая важная вещь из всей конструкции.

Не надо делать:

```text
"Ты сказал что-то неприятное"
        ↓
anger += 0.4
```

Нужно:

```text
EVENT
 ↓
Что произошло?
 ↓
Кто это сделал?
 ↓
Насколько это важно?
 ↓
Противоречит ли это моим целям/ожиданиям?
 ↓
Есть ли у меня контроль?
 ↓
Есть ли угроза?
 ↓
Есть ли личная значимость?
 ↓
Какой эмоциональный результат?
```

То есть appraisal.

Работа 2026 года по appraisal-informed emotion prediction как раз рассматривает эмоцию через expectation → violation → emotion shift и обнаруживает, что ожидания особенно важны для правильного предсказания переходов эмоционального состояния. ([ACL Anthology][2])

Например:

### Незнакомец

> «Ты тупая».

Appraisal:

```text
target = Nira
source = stranger

personal_relevance = 0.4
social_threat = 0.55
trust = 0.02
control = 0.85
```

Результат:

```text
irritation +0.25
anger +0.10
defensiveness +0.30
```

### Вова

> «Нира, ты сегодня вообще что-то тупишь».

Если trust/affection высокие:

```text
threat = 0.08
personal_relevance = 0.45
relationship_safety = 0.90
```

Результат:

```text
irritation +0.08
humor +0.15
affection -0.00
```

И Нира может ответить совершенно иначе.

Вот это уже **социальное эмоциональное поведение**, а не тег `(angry)`.

---

# 5. Эмоции должны зависеть от человека

Это критически важно для твоей идеи «знакомые / незнакомые».

Я бы ввела:

```text
Global Emotional State
        +
Relationship State[person]
        +
Current Appraisal
        +
Relevant Memories
```

То есть:

```text
GLOBAL:
mood = +0.2

VOVA:
trust = 0.95
affection = 0.82

STRANGER_A:
trust = 0.12

STRANGER_B:
trust = 0.48
```

Одна и та же фраза:

> «Ну ты даёшь».

может вызвать:

```text
Вова → amusement
Незнакомец → uncertainty
Враждебный человек → irritation
```

# 6. А память должна сама вызывать эмоции

Это следующий уровень.

Допустим, шесть часов назад человек сказал Нире:

> «Ты мне реально помогла».

Эпизод сохраняется:

```text
event = praise
target = Nira
source = person_X

emotion = joy
valence = +0.73
importance = 0.61
```

Через шесть часов:

```text
person_X joins Discord
```

ещё до новой реплики retrieval может вернуть:

```text
positive_memory:
"You helped me earlier..."
```

и emotion engine:

```text
anticipatory_affection += 0.20
trust += 0.04
```

То есть:

> человек просто появился → эмоциональный фон уже изменился.

Именно это очень сильно отличает персонажа с состоянием от обычного chatbot.

# 7. Я бы сделала две скорости эмоционального изменения

Это ещё один момент, который сейчас активно появляется в архитектурах эмоциональных агентов. Sentipolis прямо использует dual-speed emotion dynamics. ([ACL Anthology][1])

### Быстрые эмоции

Меняются за секунды:

```text
surprise
fear
anger
joy
excitement
embarrassment
```

### Медленные

Меняются постепенно:

```text
trust
affection
resentment
attachment
mood
social comfort
```

Пример:

```text
страшная фраза

fear:      0.05 → 0.72
arousal:   0.25 → 0.81

через 30 секунд:

fear:      0.72 → 0.41

через 10 минут:

fear:      0.41 → 0.12
```

Но:

```text
trust: 0.71 → 0.67
```

потому что одна страшная реплика не должна разрушить месяцы отношений.

# 8. Нужна инерция эмоций

Простейшая модель уже будет сильно лучше хаотического LLM:

```text
state_new =
    state_old * decay
    + appraisal_delta
    + memory_delta
    + social_delta
```

Но я бы сделала ещё:

```text
Δemotion × intensity
```

и ограничение:

```text
-1 ≤ state ≤ +1
```

Например:

```python
new = old * 0.92 + delta * 0.35
```

для быстрого состояния.

Для trust:

```python
new = old * 0.998 + delta * 0.01
```

То есть доверие практически не скачет.

Не надо пихать всю внутреннюю математику.

LLM достаточно видеть что-то вроде:

```yaml
  arousal: 0.42
```

# 10. И только после генерации нужен Emotion→TTS Renderer

Вот здесь появляется Fish Audio.

Это очень удачно для твоей архитектуры, потому что S2 сейчас значительно лучше подходит для этого, чем старый закрытый набор фиксированных emotion labels.

Fish Audio S2 поддерживает inline natural-language tags, причём тег может находиться не только в начале предложения, но и непосредственно перед нужным словом/фразой. Поддерживается свободное естественное описание вроде `[whispering]`, `[voice rough from crying, trying to sound normal]`, `[laughing]`, `[super happy]`. Fish также заявляет поддержку русского и более 80 языков. ([Fish Audio][3])

То есть TTS-слой можно сделать очень выразительным.

---

# 11. Но Fish tags я бы НЕ хранила как внутреннее состояние

Это очень важный архитектурный момент.

Плохо:

```text
LLM → [happy] → Fish
```

Лучше:

```text
Emotion Engine
      ↓
Semantic Emotion
      ↓
TTS Renderer
      ↓
Fish-specific tag
```

Например:

```yaml
emotion:
  primary: affection
  intensity: 0.63

delivery:
  warmth: 0.71
  energy: 0.46
  smile: 0.38
```

Renderer:

```text
affection + moderate warmth
        ↓
[soft][warm]
```

А:

```text
anger 0.82
arousal 0.88
dominance 0.77
```

может превратиться в:

```text
[angry][firm]
```

или более подробное естественное описание для S2.

Так vendor-specific Fish syntax не проникает во всю архитектуру.

---

# 12. Для S2 я бы вообще перешла от фиксированных emotion tags к expressive directives

Fish прямо указывает, что S2 не ограничен фиксированным словарём и принимает natural-language descriptions, а официальные материалы показывают комбинации вроде `[whispering] [scared]`, `[shouting] [angry]`, `[sigh] [sad]`. ([Fish Audio][4])

Поэтому у тебя может быть:

```text
[soft voice, slightly amused]
Ну конечно, ты опять это сделал...
```

или:

```text
[trying not to laugh]
Нет. Нет, я сейчас серьёзно...
```

Это намного ближе к тому, что тебе нужно для VTuber.

# 17. Ещё одна важная проблема текущего pipeline

У тебя сейчас `clean_phrase_for_tts()` предназначен для удаления мета-инструкций, скобок, emoji и т. д. 

Это потенциально конфликтует с новой системой.

Нельзя просто:

```text
LLM output
 ↓
clean_phrase_for_tts()
 ↓
Fish
```

потому что новый pipeline должен сохранить:

```text
[angry]
[soft]
[laughing]
[whispering]
```

Но при этом удалить внутренние служебные конструкции.

Поэтому нужен именно **parser**, а не sanitizer:

```text
LLM output
      ↓
Response Parser
      ├── semantic text

      ├── TTS directives
```

Это гораздо надёжнее.

# 18. И я бы вообще не заставляла LLM генерировать emotion tags

На первом этапе — особенно.

Пусть LLM отвечает:

А это две разные вещи.

# 19. Что использовать для русского языка

Здесь есть хорошие новости.

На сентябрь 2026 года есть вполне usable российский ecosystem для emotion recognition.

У Aniemore есть русские speech-emotion модели на Wav2Vec2/WavLM и комбинированные audio+text модели. Например, `wav2vec2-bert-tiny2-s-emotion-russian-resd` использует одновременно аудио и транскрипцию, то есть для твоего pipeline это концептуально интереснее простого sentiment classifier. Есть и более лёгкие варианты:


# Gemini
В текущей архитектуре проекта уже заложен сильный асинхронный фундамент (ранний barge-in, разделение потоков, буферизация реплик), однако внедрение эмоционального интеллекта и тегов синтеза вскрывает несколько системных конфликтов.

---

### Архитектурный аудит: узкие места текущей базы

* **Конфликт санитайзера и тегов Fish Audio:** В методе `clean_phrase_for_tts` прописано жесткое вырезание скобок, звездочек и псевдодействий (`*смеется*`, `\([^)]*\)`). Если LLM начнет отдавать теги вроде `(смеется)` или `(шепотом)`, санитайзер их уничтожит до отправки в TTS. Нужен парсер-разделитель (Lexer), разделяющий текст на синтезируемую речь, аудио-директивы Fish Audio и визуальные команды для аватара.


* **Дрожание просодии при потоковой нарезке фраз:** Разбиение потока токенов по знакам `. `, `! `, `? ` в `tts_queue` приводит к тому, что тег эмоции применяется только к первому предложению. Второе и третье предложения чанка отправляются в Fish Audio без контекста, из-за чего синтезатор сбрасывает интонацию в нейтральную базу.


* **Изоляция памяти от аффективного контекста:** `EpisodicStore` и `ChatMessage` сохраняют только `user`, `content` и `timestamp`. Без сохранения валентности диалога (насколько разговор был теплым, напряженным или обидным) векторный поиск извлекает факты, но теряет эмоциональный подтекст ситуации.


* **Зависание эмоционального состояния при Barge-in:** При прерывании человека срабатывает `_interrupt_jobs`. Если Нира сгенерировала фразу с сильным всплеском обиды или радости, но была перебита на первом слове, модель рискует остаться в неактуальном эмоциональном регистре без точки сброса.



---

### SOTA-архитектура эмоционального интеллекта (Сентябрь 2026)

Для локальных агентов стандартом является **гибридная модель PAD (Pleasure-Arousal-Dominance)** в сочетании с двухконтурным циклом обработки (быстрый рефлекс + когнитивная рефлексия).

Вектор эмоций $E$ описывается тремя непрерывными координатами в диапазоне $[-1.0, 1.0]$:

* **$P$ (Pleasure / Валентность):** от глубокого негатива/грусти ($-1.0$) до восторга и тепла ($+1.0$).
* **$A$ (Arousal / Возбуждение):** от сонного покоя/апатии ($-1.0$) до паники, истерики или эйфории ($+1.0$).
* **$D$ (Dominance / Уверенность):** от чувства уязвимости/подчинения ($-1.0$) до доминирования и дерзости ($+1.0$).

Динамика состояния во времени подчиняется экспоненциальному возврату к гомеостазу (базовому характеру Ниры $E_{base}$):

$$E_{t} = (E_{t-1} - E_{base}) \cdot e^{-\lambda \Delta t} + E_{base} + \sum \Delta E_{stimulus}$$

где $\lambda$ — коэффициент остывания (эмоциональная инерция), а $\Delta E_{stimulus}$ — суммарный импульс от входящей реплики, персоны собеседника и извлеченных воспоминаний.

---

### Базовые эмоции для Fish Audio и сопоставление с PAD

Fish Audio отлично подхватывает как русские, так и латинские маркеры просодии. Рекомендуется ограничить модель фиксированным словарем тегов, жестко привязанным к окнам PAD:

| Эмоция / Регистр | Координаты PAD | Тег Fish Audio (RU / EN) | Влияние на темп и подачу |
| --- | --- | --- | --- |
| **Нейтральный (база)** | $P: 0.1, A: 0.0, D: 0.0$ | *(без тега)* | Естественный разговорный темп |
| **Радость / Тепло** | $P: 0.8, A: 0.5, D: 0.2$ | `(радостно)` / `[laugh]` | Ускорение, повышение питча, улыбка |
| **Сарказм / Подколка** | $P: 0.2, A: 0.3, D: 0.6$ | `(ухмыляется)` / `[snicker]` | Замедление ударных слогов, легкий смешок |
| **Смущение / Неловкость** | $P: 0.3, A: 0.4, D: -0.6$ | `(смущенно)` / `(шепотом)` | Падение громкости, прерывистость |
| **Грусть / Сочувствие** | $P: -0.7, A: -0.5, D: -0.3$ | `(тихо)` / `[sigh]` | Низкий тон, паузы, придыхание |
| **Раздражение / Обида** | $P: -0.6, A: 0.7, D: 0.5$ | `(недовольно)` / `(фыркает)` | Рубленые фразы, жесткая компрессия |
| **Удивление / Шок** | $P: 0.0, A: 0.9, D: -0.2$ | `(опешив)` / `(удивленно)` | Резкий вздох в начале, ускоренный темп |

### Архитектурный модуль `EmotionalCore`

Внедрите менеджер состояний в `src/memory/identity/emotional_core.py`:

```python
import time
import math
from typing import Dict, Tuple

class EmotionalCore:
    def __init__(self):
        # Базовый характер Ниры: дружелюбная, любопытная, слегка дерзкая
        self.base_state = {"P": 0.25, "A": 0.1, "D": 0.15}
        self.current_state = self.base_state.copy()
        self.last_update_ts = time.time()
        self.decay_rate = 0.02  # Возврат к норме за ~90-120 секунд

    def decay(self) -> None:
        now = time.time()
        dt = now - self.last_update_ts
        self.last_update_ts = now
        for dim in ["P", "A", "D"]:
            diff = self.current_state[dim] - self.base_state[dim]
            self.current_state[dim] = self.base_state[dim] + diff * math.exp(-self.decay_rate * dt)

    def apply_stimulus(self, delta_p: float, delta_a: float, delta_d: float) -> None:
        self.decay()
        self.current_state["P"] = max(-1.0, min(1.0, self.current_state["P"] + delta_p))
        self.current_state["A"] = max(-1.0, min(1.0, self.current_state["A"] + delta_a))
        self.current_state["D"] = max(-1.0, min(1.0, self.current_state["D"] + delta_d))

    def get_prompt_injection(self, speaker_id: str, is_known: bool) -> str:
        self.decay()
        p, a, d = self.current_state["P"], self.current_state["A"], self.current_state["D"]
        
        # Динамика «Свой / Чужой»
        social_context = "Собеседник — близкий (Создатель)." if is_known else "Собеседник — незнакомец (дистанция, настороженность)."
        
        return (
            f"\n### Внутреннее эмоциональное состояние ###\n"
            f"- Состояние (PAD): Удовольствие={p:.2f}, Возбуждение={a:.2f}, Уверенность={d:.2f}\n"
            f"- Социальная связь: {social_context}\n"
            f"- Инструкция по Fish Audio: Если уместно, начни фразу с акустического маркера: "
            f"`(радостно)`, `(ухмыляется)`, `(шепотом)`, `(недовольно)`, `(опешив)`, `(тихо)` или тега `[laugh]`.\n"
        )

```

### Интеграция в Data Flow и исправление пайплайна

**1. Санитайзер и фильтрация (`nira.py`):**
Разделите очистку на белый список тегов синтеза и вырезание мусора:

```python
import re

ALLOWED_FISH_TAGS = {
    "(радостно)", "(ухмыляется)", "(смущенно)", "(шепотом)",
    "(тихо)", "(недовольно)", "(опешив)", "(удивленно)",
    "[laugh]", "[sigh]", "[giggle]", "[snicker]"
}

def clean_phrase_for_tts(self, text: str) -> str:
    # 1. Извлекаем и временно маскируем валидные теги Fish Audio
    tag_placeholders = {}
    def mask_tag(match):
        tag = match.group(0).lower()
        if tag in ALLOWED_FISH_TAGS:
            placeholder = f"__TAG_{len(tag_placeholders)}__"
            tag_placeholders[placeholder] = tag
            return placeholder
        return ""  # Удаляем невалидные скобки/действия

    text = re.sub(r'(\([^\)]+\)|\[[^\]]+\])', mask_tag, text)
    
    # 2. Вырезаем REQUEST:..., смайлы, markdown, лишние звездочки
    text = re.sub(r'REQUEST:[^\n]*', '', text)
    text = re.sub(r'[\*\_~`]', '', text)
    text = re.sub(r'(?::\)|:D|<3|xd|\^_-\)', '', text, flags=re.IGNORECASE)
    
    # 3. Возвращаем одобренные теги на место
    for placeholder, original_tag in tag_placeholders.items():
        text = text.replace(placeholder, original_tag)
        
    return text.strip()

```

**2. Удержание эмоционального контекста при стриминге:**
Если первое предложение реплики получило тег `(шепотом)`, сохраните этот тональный маркер в локальной переменной генератора `active_turn_emotion`. Если последующие предложения не имеют собственного тега, но $Arousal > 0.5$ или $Dominance < -0.4$, автоматически подставляйте активный маркер в начало каждого предложения чанка перед отправкой в WebSocket Fish Audio.

**3. Влияние памяти и окружения на эмоции:**

* **Идентификация спикера:** При распознавании голоса Создателя через `configs/known_users.json` вызывайте `EmotionalCore.apply_stimulus(+0.3, 0.0, -0.1)` (рост доверия, снятие оборонительного доминирования). Для незнакомого спикера — `apply_stimulus(-0.2, +0.2, +0.3)` (включение легкого скепсиса и самоконтроля).


* **Воспоминания:** Добавьте поле `emotional_valence: float` в `EpisodicStore`. При извлечении через `VectorRetrieval` суммируйте валентность найденных нод: воспоминание о совместной победе в игре дает импульс $+P$, а воспоминание об ошибке или ссоре смещает вектор в сторону $-P$ и $+A$.



Готовы ли вы перейти к реализации классификатора эмоций входящей речи (через анализ тональности текста или аудиопросодии Whisper), чтобы импульсы PAD рассчитывались автоматически на каждый ответ собеседника?

# Deepseek
Отличный проект! У `Нира` очень продуманная архитектура, особенно радует асинхронный пайплайн и модульность. Внедрение эмоционального интеллекта — это логичный и мощный шаг, который выведет её на совершенно новый уровень.

Давайте разберем все по порядку.

### 1. Критический анализ архитектуры: что уже хорошо, а что требует внимания

На данный момент архитектура `Нира` имеет ряд сильных сторон и несколько потенциальных «узких горлышек», которые стоит учесть перед добавлением новой сложной системы.

**Что уже отлично:**

*   **Сквозной асинхронный пайплайн**: Это идеальная основа. Обработка речи (STT) → генерация (LLM) → синтез (TTS) не блокирует друг друга, что критично для живого диалога.
*   **Система раннего прерывания (Barge-in)**: Механизмы `_interrupt_jobs` и `_stop_local_speakers` обеспечивают мгновенную реакцию на речь пользователя.
*   **Интеллектуальный буфер речи (`_buffer_voice_turn`)**: Склейка фраз одного говорящего с учетом пауз — очень правильный подход для обработки естественной речи.
*   **Модульность операций**: `OperationManager` и класс `Operation` позволяют легко подменять компоненты (STT, T2T, TTS), что делает систему гибкой и готовой к экспериментам.
*   **Продуманная система памяти**: 4-уровневая архитектура (эпизодическая, семантическая, рабочая, рефлексивная) — это фундамент для развития личности.
*   **Фильтрация промптов**: Вырезание комментариев разработчика `<!-- -->` перед отправкой в LLM — отличная инженерная практика.

**На что стоит обратить внимание перед внедрением эмоций:**

1.  **Нагрузка на GPU (RTX 5070 12GB)**: Это, пожалуй, самый критичный пункт. Сейчас ваш GPU уже загружен:
    *   **LLM (LlamaCpp)**: Инференс модели.
    *   **STT (Faster-Whisper)**: Распознавание речи.
    *   **Потенциально TTS (Fish Audio)**: Если вы используете локальную модель, она тоже потребует ресурсов.
    *   Добавление **модели для детекции эмоций** (например, на базе ruBERT) может создать серьезную конкуренцию за видеопамять. **Рекомендация**: Рассмотрите возможность выгрузки детекции эмоций на CPU или использования более легковесных моделей (например, `distilrubert`). Также можно интегрировать детекцию эмоций непосредственно в промпт LLM, чтобы не запускать отдельную модель, но это увеличит потребление токенов.

2.  **Управление состоянием (State Management)**: Сейчас эмоциональное состояние `Нира` не централизовано. Чтобы эмоции были последовательными и влияли на все аспекты поведения, необходимо создать единый **`EmotionState`**, который будет:
    *   Хранить текущую эмоцию и её интенсивность.
    *   Обновляться на основе входных данных (текст/голос пользователя).
    *   Постепенно «затухать» до нейтрального состояния.
    *   Быть доступным для всех компонентов системы (промптер, LLM, TTS).

3.  **Сквозная передача эмоций**: Сейчас пайплайн линейный: `STT → LLM → TTS`. Для эмоций его нужно расширить, чтобы информация об эмоциональном состоянии передавалась от детектора к генератору и далее к синтезатору речи. Это можно реализовать через контекстное поле в `Prompter` или через глобальное состояние `Nira`.

### 2. Актуальные решения для эмоционального ИИ на русском языке (сентябрь 2026)

На 2026 год для реализации эмоционального интеллекта на русском языке есть несколько перспективных направлений:

*   **Продвинутые эмоциональные движки**: Появились готовые решения, которые моделируют целый психологический пайплайн. Например, **Blaniel** использует когнитивную модель OCC, колесо эмоций Плутчика и модель «Большой пятерки» для создания глубоких эмоциональных агентов. Другой пример — **Soma Protocol**, библиотека для создания агентов с идентичностью, памятью и эмоциональным интеллектом.
*   **Специализированные модели для русского языка**: Исследования 2026 года показывают, что разрыв в понимании эмоций между английским и русским языками у LLM все еще существует. Поэтому для надежной детекции эмоций лучше использовать модели, дообученные на русских данных, например, **ruBERT**, настроенный на датасете **EmpatheticDialogues** (переведенном на русский и размеченном по 32 эмоциональным категориям).
*   **Мультимодальный подход**: Ведущие российские разработки, такие как **GigaChat Audio** от Сбера или платформа **HL-EAI** от МГУ, делают ставку на мультимодальность — анализ эмоций одновременно из текста и голоса. Это дает гораздо более полную картину.
*   **Эмоциональные TTS**: Fish Audio здесь является одним из лидеров. Модели S2 (и даже S1) позволяют управлять более чем 64 эмоциональными выражениями с помощью простых тегов.

### 3. План внедрения эмоциональной системы в проект «Нира»

Вот конкретный, пошаговый план, как интегрировать эмоции в вашу архитектуру.

#### Шаг 1: Выбор базовых эмоций

Не нужно изобретать велосипед. Fish Audio уже имеет обширный список поддерживаемых эмоций. Рекомендую взять за основу **8 базовых эмоций из колеса Плутчика** (или их русскоязычные аналоги, понятные вашей LLM), которые отлично лягут на теги Fish Audio:

1.  **Радость** (`[happy]` / `[excited]`)
2.  **Грусть** (`[sad]`)
3.  **Гнев** (`[angry]`)
4.  **Страх** (`[scared]`)
5.  **Удивление** (`[surprised]`)
6.  **Отвращение** (`[disgusted]`)
7.  **Доверие** / **Спокойствие** (`[calm]`)
8.  **Ожидание** / **Любопытство** (`[curious]`)

Этого набора достаточно для начала. Вы всегда сможете расширить его до 24+ эмоций позже.

#### Шаг 2: Создание системы управления эмоциями (`EmotionEngine`)

Вам нужен новый модуль, например, `src/emotion/engine.py`. Он должен выполнять три ключевые функции:

**А. Детекция эмоций собеседника:**
*   Создайте класс, который принимает на вход текст (и, в перспективе, аудио-фичи) от пользователя.
*   Используйте легковесную модель, например, `rubert-tiny` или `distilrubert`, дообученную на русскоязычном эмоциональном датасете (см. исследования ВШЭ).
*   Результат — предсказанная эмоция и её уверенность (например, `{'emotion': 'happy', 'confidence': 0.85}`).
*   *Альтернатива (проще):* Включить в системный промпт инструкцию для LLM определять эмоцию пользователя и передавать её в структурированном виде. Это сэкономит ресурсы GPU, но может быть менее надежным.

**Б. Формирование внутреннего состояния `Нира`:**
*   Ведите массив из `N` последних эмоциональных состояний (как своих, так и пользователя).
*   Реализуйте механизм **«эмоционального затухания» (decay)**, чтобы эмоции `Нира` постепенно возвращались к нейтральному состоянию, если нет стимулов.
*   Добавьте **«эмоциональную инерцию»** — резкие перепады должны быть редки, если только пользователь специально не провоцирует `Нира`.

**В. Интеграция с памятью:**
*   Эмоции должны сохраняться в **эпизодической памяти** вместе с самим диалогом.
*   При извлечении воспоминаний, их эмоциональная окраска должна влиять на текущее состояние `Нира`. Например, если она вспомнила грустный разговор, её настроение может ненадолго ухудшиться.

#### Шаг 3: Интеграция в пайплайн

1.  **В `Prompter`**: Добавьте блок в системный промпт, который описывает текущее эмоциональное состояние `Нира`.
    ```
    ### Current Emotional State ###
    You are feeling [calm] with a hint of [curious]. Your mood is positive.
    The user seems to be [sad] right now.
    ```
    Это направит генерацию LLM в нужное русло.

2.  **В `response_pipeline` (`Nira`)**:
    *   После получения ответа от LLM, но до отправки в TTS, пропускайте текст через **«эмоциональный санитайзер»**.
    *   Этот модуль должен анализировать текст и содержимое промпта, чтобы расставить корректные теги эмоций Fish Audio **в начале каждого предложения**, согласно документации.
    *   *Пример:* LLM генерирует: `"Это потрясающая новость! Я так рада за тебя."` → Санитайзер преобразует: `[excited] Это потрясающая новость! [happy] Я так рада за тебя.`

3.  **В `FishAudioTTS`**: Убедитесь, что ваш класс-операция корректно передает теги в квадратных скобках `[]` (для модели S2) в API Fish Audio.

#### Шаг 4: Динамическое изменение эмоций

Чтобы `Нира` реагировала на разных людей и воспоминания:

*   **На разных людей**: Интегрируйте детекцию эмоций с системой распознавания пользователей (`resolve_speaker_name`). Ведите для каждого известного пользователя историю его эмоциональных состояний. Если `Нира` знает, что `Вова (Папа)` часто бывает в хорошем настроении, она может изначально настраиваться на более позитивный лад при общении с ним.
*   **На воспоминания**: При поиске в семантической или эпизодической памяти, извлекайте не только факты, но и связанные с ними эмоции. Если `Нира` вспоминает, что `Настя (Мама)` расстроилась из-за чего-то в прошлом разговоре, она может проявить больше эмпатии в текущем диалоге.

### 4. Рекомендуемые улучшения архитектуры

1.  **Добавить `EmotionService`**: Создайте новый сервис, который будет центральной точкой для всей эмоциональной логики. Это снизит связанность кода.
2.  **Расширить `Prompter`**: Добавьте методы для динамического обновления эмоционального блока в промпте на основе состояния `EmotionService`.
3.  **Модифицировать `clean_phrase_for_tts`**: Переименуйте или расширьте его функционал, чтобы он не только *чистил* текст, но и *обогащал* его эмоциональными тегами.
4.  **Добавить телеметрию**: В `get_pipeline_telemetry` и на WebSocket добавьте метрики по эмоциональному состоянию, чтобы видеть, как оно меняется во времени.

Эмоциональный интеллект — это та часть, которая превратит `Нира` из просто умного собеседника в живого и запоминающегося персонажа. Удачи в реализации!

# Groq
Это не задача «добавить теги в промпт». В текущей архитектуре Ниры эмоции сломаются о санитайзер, god-object `Nira` и отсутствие **состояния**, отдельного от LLM. Ниже — аудит, что есть в сентябре 2026, и конкретная схема, которую можно вшить в пайплайн.

---

## 1. Проблемы архитектуры уже сейчас

Документ сильный как каталог модулей. Как **живая система характера** он ещё не собран: часть блоков описана как существующие, но в сквозном data flow их нет.

### Критично для эмоций

**Санитайзер уничтожит Fish-теги.**  
`clean_phrase_for_tts()` режет скобки, `REQUEST:`, эмодзи, `*действия*`. У Fish S1 теги — `(happy)`, у S2 — `[sad][whispering]`. Сейчас любой нормальный тег либо вырежется, либо превратится в мусор. Это **первый блокер**. Пока санитайзер «чистит речь», TTS останется плоским.

`ChatMessage` тоже чистит незакрытые скобки и рудименты. Если LLM начнёт писать `[грустно] ...`, история либо загрязнится тегами, либо потеряет их. Нужны **два представления одной реплики**: `text_spoken` (для памяти/промпта) и `text_tts` (с тегами, только в TTS-очередь).

**Эмоция просится у модели, а не считается.**  
Сейчас характер — статический `character.md`. LLM каждый ход «играет» настроение заново. Это даёт качание: одно и то же «привет» то радостное, то холодное. В 2026 консенсус обратный: **аффект — отдельный контроллер**, LLM только говорит из уже посчитанного состояния.

**Память нарисована, в пайплайн не вставлена.**  
Раздел 7 описывает episodic / semantic / working / identity. `get_sys_prompt()` собирает только `instruction.md` + `character.md` + `scene_*.md` + Discord + interrupted speech + историю. Воспоминания не влияют ни на настроение, ни на тон к человеку. Без этой связки «реакция на память» невозможна.

**`Nira` — god object.**  
Очередь, barge-in, склейка хода, санитайзер, Discord-статус, имена, TTS-worker — всё в одном синглтоне. Affective layer туда не влезает без превращения ядра в болото. Эмоции должны быть отдельным сервисом с узким API, как STT/T2T.

**`REQUEST:` в речевом потоке — хрупкий хак.**  
Early-stop по подстроке конфликтует с любыми скобочными/квадратными тегами. Инструменты и речь должны идти разными каналами (structured output / tool tokens), а не «скажи REQUEST: и мы обрежем».

### Системные дыры под цели 1–11

| Цель | Что в спеке | Что ломается |
|---|---|---|
| Устойчивый характер | `character.md` | Нет трейтов как чисел, только проза. Модель «переигрывает» |
| Осознание в моменте | Interrupted Speech Memory | Нет интероцепции: энергия, слушает/говорит, кто в комнате как **внутреннее состояние** |
| Развитие личности | `identity/` | Нет контура записи: диалог → рефлексия → изменение трейта |
| Эмоциональность | нет модуля | Нет appraisal, mood, decay |
| Память | 4 уровня на бумаге | Не подключена к промптеру |
| Несколько людей | `known_users.json` | Только алиасы. Нет вектора отношений |
| Идентификация по голосу | resolve_speaker_name | Это словарь имён, не speaker embedding |
| Дообучение на диалогах | заявлено | Нет датасета, фильтра, цикла fine-tune |

### Операционные риски

- **VRAM RTX 5070 12 GB.** Faster-Whisper + llama-server уже делят карту. Третья большая модель «просто так» не встанет. Эмоции с голоса — маленький классификатор (GigaAM-Emo), не ещё один LLM.
- **`is_listening: bool` слишком грубый.** Возбуждённая Нира должна перебивать иначе, чем спокойная. Barge-in должен модулироваться arousal, не флагом.
- **Склейка фраз 750/1400 мс** не знает эмоции собеседника. Человек в слезах ≠ человек задал вопрос.
- Документ местами описывает **желаемое как существующее**. Это опасно для агента-разработчика: он «допилит» модуль, которого нет.

Итог: пайплайн голоса зрелый. Психика персонажа — нет. Эмоции нельзя «прикрутить тегами в генерацию», их надо поставить **перед** T2T и **после** него, как отдельный слой.

## 2. Сентябрь 2026: что реально работает

Поле разделилось. «LLM изображает эмоцию в промпте» — устаревший путь. Актуальный — **модульный аффект как control layer**.

### Архитектурный консенсус 2026

1. **Affect inference → relation → generation → safety**  
   IEEE TAC, май 2026: эмпатия — пайплайн, не свойство модели. LLM симулирует когнитивную эмпатию, не «чувствует». Для vTuber этого достаточно, если состояние **явное и стабильное**.

2. **Разделить мгновенный аффект и связь**  
   SciTePress, 4 сент 2026: модели путают «собеседник сейчас зол» с «отношения испортились». Нужны две оси:
   - *emotion* — секунды/минуты
   - *bond* — дни/месяцы, GraphRAG / профиль человека

3. **ALMA: emotion / mood / personality**  
   Короткое (эмоция), среднее (настроение), длинное (характер). Без трёх горизонтов Нира будет либо плоской, либо биполярной.

4. **Appraisal до ответа (Chain-of-Emotion / OCC)**  
   Сначала оценка события: кто, к кому, ожидаемо ли, затрагивает ли ценности. Потом речь. Не наоборот.

5. **PAD как внутренние числа, не 64 ярлыка**  
   Pleasure / Arousal / Dominance — непрерывное состояние. Дискретный тег для Fish — **проекция** PAD, не источник истины.

6. **Интероцепция**  
   Nature Machine Intelligence, авг 2026: внутренние переменные (энергия, скука, безопасность) — first-class state, как гомеостаз. У тебя уже есть зачатки: `is_listening`, interrupted speech. Их надо расширить, а не прятать в промпт.

7. **LLM не имеет эмоций**  
   *Nature Human Behaviour*, 24 авг 2026. Практический вывод: не спрашивай модель «что ты чувствуешь?». Считай состояние снаружи, отдай модели как факт.

Для vTuber это совпадает с тем, как живут сильные клоны Neuro: **отдельный emotional state + фильтр + TTS**, а не «характер в system prompt».

### Русский язык: что брать, что не брать

| Задача | Лучшее на сент. 2026 | Зачем |
|---|---|---|
| Эмоция **в голосе** собеседника | **GigaAM-Emo** (SberDevices, Dusha: anger/happiness/sadness/neutral, +15% Macro F1) | Единственный сильный открытый SER именно для русского. Маленькая, можно CPU/очередь после STT |
| Эмоция **в тексте** | **ruBERT-tiny2-ru-go-emotions** (28 меток GoEmotions) | Дешёвый multi-label на реплике после Whisper |
| Мультимодальный облачный | GigaChat Audio (июль 2026, ~80% emotion acc) | Не для локального ядра; запасной путь |
| TTS-эмоция | **Fish S2 / S2.1-Pro**, теги `[...]` | Русский в списке языков; S2 понимает и EN, и свободный NL |
| Генерация | Твой LlamaCpp / Groq | Эмоцию **не** доверять модели как единственному источнику |

Whisper + «угадай настроение по тексту» на русском слабый: теряется интонация. Текст «ну ок» может быть и теплом, и обидой. Для Ниры обязателен **голосовой** классификатор.

GigaAM-Emo даёт 4 грубых класса — этого мало для персонажа, но достаточно как **сенсор arousal/valence**. Дальше appraisal (кто говорит, память, отношения) расширяет до рабочего набора.

## 3. Fish Audio: как теги устроены на самом деле

Не путать модели.

| | **S1** | **S2 / S2.1-Pro** |
|---|---|---|
| Синтаксис | `(happy)` | `[happy]` или свободный `[slightly sad, almost whispering]` |
| Словарь | фиксированные 64+ | открытый NL, 15k+ описаний |
| Куда ставить эмоцию | начало предложения | любое место, действует до следующего тега |
| Русский | да, 13 языков | да, ~80 языков, автодетект |
| Интенсивность | набор близких ярлыков | `[slightly]` / `[very]` / `[extremely]` |

Правила, которые важны для твоего стриминга по предложениям:

- **Один primary emotion на предложение.** Не больше ~3 маркеров (эмоция + тон + звук).
- Эмоция — в начало куска, который уходит в `tts_queue`. Это совпадает с нарезкой по `. ? ! \n`.
- Тон и эффекты (`[whispering]`, `[sigh]`, `[laughing]`, `[pause]`) можно в середину.
- Конфликтующие теги (`[happy][depressed]`) запретить на уровне контроллера.
- После `[laughing]` лучше дать речевой наполнитель: «ха», «хех», иначе модель иногда «глотает» смех.
- Теги **не произносятся**, если синтаксис верный. Сломанный тег Нира прочитает вслух — это катастрофа в эфире.

**Русские vs английские теги.** S2 умеет `[шёпотом]`, `[вздохнув]`. На практике английские стабильнее (больше обучения). Для продакшена Ниры:

- канон контроллера — **английские** теги: `[soft]`, `[sad]`, `[chuckling]`;
- русский NL (`[тихо, почти шепотом]`) — только как эксперимент на S2;
- в `character.md` и истории диалога тегов **нет вообще**.

Не отдавай LLM 64 ярлыка. Она начнёт ставить `[hysterical]` на «ты снова забыл чай». Словарь TTS шире, чем словарь **психики** персонажа.

## 4. Какие эмоции заводить Нире

Три слоя. Путать их — главная ошибка.

### A. Внутреннее состояние (непрерывное, не теги)

```
PAD:
  P (valence)   [-1..1]  приятно ↔ неприятно
  A (arousal)   [0..1]   спокойствие ↔ возбуждение
  D (dominance) [-1..1]  уступает ↔ ведёт разговор

Гомеостаз:
  energy, safety, boredom, social_openness
```

Базовый mood Ниры (из характера): слегка +P, средний A, D зависит от человека. С Папой — выше D и игривость. С незнакомцем в Discord — ниже D, выше осторожность.

### B. Рабочий набор discrete-эмоций (12, не 64)

Этого хватает и для лица, и для голоса, и для памяти.

| ID | Когда вспыхивает | Fish (канон) | Лицо / Live2D |
|---|---|---|---|
| `neutral` | базовая | без тега или `[calm]` | idle |
| `warm` | свой человек, забота | `[soft tone]` / `[empathetic]` | soft smile |
| `playful` | подкол, игра | `[amused]` + `[chuckling]` | grin |
| `curious` | новое, вопрос | `[curious]` | head tilt |
| `surprised` | неожиданность | `[surprised]` / `[gasping]` | brows up |
| `excited` | хорошая новость, Папа дома | `[excited]` / `[delighted]` | big open |
| `sad` | боль собеседника, тяжёлая память | `[sad]` / `[slightly sad]` | down |
| `worried` | угроза, ссора | `[worried]` / `[anxious]` | tense |
| `annoyed` | повтор, грубость, игнор | `[frustrated]` (не `[furious]`) | unamused |
| `embarrassed` | промах, комплимент в лоб | `[embarrassed]` | blush |
| `nostalgic` | достали воспоминание | `[soft tone]` + чуть `[sad]` | distant |
| `sarcastic` | черта характера, не злость | `[sarcastic]` | smirk |

Полный гнев (`angry`/`furious`), истерика, презрение — **не в базовый набор**, пока не опишешь, в каких ситуациях Нира имеет право. Иначе TTS будет орать на семью.

Паралингвистика отдельно, это не эмоции:

`[laughing]` `[chuckling]` `[sighing]` `[pause]` `[long pause]` `[whispering]` `[inhale]` `[soft tone]` `[emphasis]`

### C. Интенсивность — 3 ступени

`low / mid / high` → `[slightly X]` / `[X]` / `[very X]`

Переход только на соседнюю ступень за один ход, кроме шока (surprised/scared). Это и есть «живой», а не «случайный» характер.

## 5. Куда это ставится в пайплайне

Эмоции — **не роль OpRoles**. Это оркестратор рядом с `Nira`, как `AffectEngine`.

```
микрофон / Discord
        │
        ├─ VAD ── POST /speech_start ── barge-in
        │                                 ▲
        │                                 │ arousal ↑ → легче перебить
        ▼
     STT (Whisper)
        │
        ├─ GigaAM-Emo (PCM того же сегмента) → user_affect {P,A,label}
        ├─ ruBERT-GoEmotions (текст)         → user_text_emotions[]
        ▼
  Voice Turn Buffer  +  speaker_id
        │
        ▼
  AffectEngine.appraise(event)
        │  читает: кто говорит, bond, память, mood Ниры, сцена
        │  пишет:  nira.PAD, nira.emotion, nira.intensity, display_intent
        ▼
  Prompter
        │  блок ### Affective State ###  (числа + 1-2 предложения)
        │  блок ### Relational ###       (этот человек: тепло, доверие)
        │  блок ### Recalled Memory ###  (если вспыхнула память)
        │  истории — БЕЗ тегов Fish
        ▼
  T2T (LLM)
        │  генерит только русскую речь + опционально
        │  скрытые маркеры действий, НЕ Fish-теги
        ▼
  AffectRenderer
        │  PAD + emotion + текст → [fish tags] на каждое предложение
        │  text_spoken → память / чат
        │  text_tts    → tts_queue
        ▼
  Fish Audio  →  колонки / Discord
        │
        └─ expression event → Live2D / VRM (когда появится лицо)
```

### Контракт `AffectEngine` (узкий)

```python
class AffectSnapshot:
    speaker: str
    user_pad: tuple[float, float, float]
    user_label: str
    nira_pad: tuple[float, float, float]
    nira_emotion: str          # из 12
    nira_intensity: str        # low|mid|high
    display_tag: str           # канонический Fish, напр. "[slightly sad]"
    paralinguistics: list[str] # ["chuckling"] 
    recalled_memory_id: str | None
    interruptibility: float    # 0..1, в barge-in

class AffectEngine:
    async def on_user_turn(self, turn: VoiceTurn) -> AffectSnapshot: ...
    async def on_memory_hit(self, mem) -> None: ...
    async def tick(self, dt: float) -> None:   # decay к mood
    def snapshot(self) -> AffectSnapshot: ...
    def render_tts(self, sentence: str, snap: AffectSnapshot) -> str: ...
```

`Nira.response_pipeline` только:

1. `snap = affect.snapshot()`
2. промптер кладёт `snap` в системный блок
3. стрим режется на предложения как сейчас
4. `tts_queue.put(affect.render_tts(sentence, snap))`
5. после хода `affect.tick()` + запись эпизода с эмоцией

### Что менять в существующем коде

1. **`clean_phrase_for_tts`** — белый список: не трогать `\[[^\]]+\]` из канона. Резать только `REQUEST:`, эмодзи, `*действия*`, markdown. Скобки `(...)` по-прежнему резать (чтобы S1-мусор и ремарки не озвучивались), **если вы на S2**.
2. **Два поля сообщения.** В историю — чистый русский. В TTS — с тегами. Иначе модель начнёт имитировать теги в следующем ходе.
3. **Промпт.** Явно: «Не пиши эмодзи, звёздочки, скобки, [теги]. Твоё состояние уже задано. Говори из него.»
4. **Barge-in.** `interruptibility = f(nira.A, is_listening, who)`. Высокий arousal + Папа = можно перебить. Низкий + «дай расскажу» = держать паузу дольше 1400 мс.
5. **VRAM.** GigaAM-Emo гонять **после** STT, на CPU или в окне, когда Whisper отдал сегмент. Не держать три модели на 12 GB одновременно.
6. **Не класть Fish-теги в LLM.** Модель врёт и не держит словарь. `AffectRenderer` — детерминированный маппинг. LLM может намекнуть скрытым служебным полем (`laugh=1`), и то лучше начать без этого.

Пример рендера:

```
вход:  "Ты опять это сделал? Ну Вов..."
snap:  emotion=playful, intensity=mid, who=Вова, bond.warmth=0.9
выход: "[chuckling] Ты опять это сделал? [amused] Ну Вов..."
```

Тот же текст, незнакомый в Discord, bond.warmth=0.1:

```
"[curious] Ты опять это сделал? Ну, ладно..."
```

## 6. Кто контролирует динамику

Один модуль, четыре памяти.

### 6.1. Горизонты (ALMA)

```
emotion   τ ≈ 15–90 с     вспышка на реплику
mood      τ ≈ 20–90 мин   инерция сессии
personality  дни/недели   identity/beliefs, редко
bond[user]   сессии       тепло, доверие, familiar
```

Каждый tick:

```
PAD_emotion += appraisal_delta
PAD_emotion  = lerp(PAD_emotion, PAD_mood, λ_decay)   # тянет к настроению
PAD_mood     = lerp(PAD_mood, PAD_personality, μ)     # очень медленно
```

Без decay Нира «залипнет» в грусти на весь вечер. Без mood — будет дёргаться каждые 3 секунды.

### 6.2. Appraisal (почему вспыхнуло)

На каждое событие (реплика, вход в канал, хит памяти, barge-in, тишина):

| Вопрос | Откуда |
|---|---|
| Кто источник? | `resolve_speaker_name` + `known_users` |
| Что с его голосом? | GigaAM-Emo |
| Что в тексте? | GoEmotions + правила («стой», «послушай») |
| Касается ли ценностей Ниры? | `beliefs` / character |
| Ожидаемо ли? | working memory + last N |
| Есть ли эпизод? | semantic/vector retrieval |
| Какой bond? | `RelationshipStore[user]` |

Правила, не LLM, для ядра (быстро, предсказуемо):

- собеседник `sad` + высокий bond → Нира `warm`/`sad`, intensity ≤ его
- собеседник `angry` + bond высокий → `worried`, не зеркалить ярость
- собеседник `angry` + незнакомец → `calm` + ниже D, короткие фразы
- комплимент Нире → `embarrassed` (характер), не `proud`
- хит старой памяти с Папой → `nostalgic` + `warm`, даже если тема бытовая
- долгая тишина → `boredom↑`, может самой заговорить (цель «осознание в моменте»)
- «продолжай» после barge-in → не сбрасывать emotion, стыковать с `_assistant_last_partial_reply`

LLM-appraisal (Chain-of-Emotion) — **второй этап**, маленьким/дешёвым вызовом, только если правила не уверенны. На 5700X3D+5070 не делать второй полный прогон 70B на каждую реплику.

### 6.3. Отношения, не только эмоция

В `known_users.json` сейчас имена. Нужен `RelationshipStore`:

```json
{
  "id": "vova",
  "display": "Вова (Папа, Создатель)",
  "warmth": 0.92,
  "trust": 0.95,
  "familiarity": 1.0,
  "dominance_allowed": 0.8,
  "sass_allowed": 0.9,
  "formality": 0.05,
  "last_shared_mood": "playful",
  "soothing_policy": "tease_then_care"
}
```

Незнакомец: warmth 0.2, trust 0.3, sass 0.1, formality 0.6, emotion default `curious`/`calm`.

После сессии — тихий апдейтер (не в hot path):

- взаимная шутка → warmth += ε
- грубость, игнор → warmth -= ε, safety -= ε
- раскрытие личного → trust += ε  
Клампы узкие. Характер не должен «разлюбиться» за один вечер — это как раз ошибка, о которой пишет статья про relationship-aware agents.

### 6.4. Память как эмоциональный триггер

Эпизод хранить так:

```python
EpisodicRecord(
  t, user, text,
  user_emotion, nira_emotion,
  pad, salience,  # salience = |ΔPAD| + personal_relevance
)
```

Retrieval: не только cosine текста, а **текст × свежесть × salience × кто в комнате**.

Если достали воспоминание с |salience| > порога:

1. `AffectEngine.on_memory_hit`
2. mood сдвигается слабее, чем emotion (память трогает, но не ломает вечер)
3. в промпт — 1–2 предложения памяти **и** пометка `nostalgic/warm/worried`
4. renderer ставит мягкие теги, не `[hysterical]`

Так Нира «живо» реагирует на прошлое, не пересказывая лог.

### 6.5. Рефрактерность (важно для стрима)

Пока доминирует emotion, она **смещает восприятие** следующего хода (EMAD, 2026). Если Нира `annoyed`, нейтральное «ну ладно» не должно мгновенно сделать её `warm`. Это и есть характер, а не вежливый ассистент.

Исключение: явные repair-сигналы («прости», смех Папы, объятие в тексте) — разрешённый быстрый спуск.

**Этап 2 — сенсор**  
GigaAM-Emo на сегмент PCM + GoEmotions на текст. Писать в телеметрию дашборда (`/api/pipeline`). Ещё не рулить характером, только смотреть.

**Этап 3 — AffectEngine + PAD + decay**  
Подключить к `response_pipeline` и barge-in. Промпт-блок состояния.

**Этап 4 — RelationshipStore**  
Расширить `known_users.json`. Разные политики для Вовы, Насти, Discord-гостей.

**Этап 5 — память**  
Salience на эпизодах, hit → nostalgic/warm/worried. Вот здесь появляется «осознание в моменте».

**Этап 6 — лицо и стрим**  
Те же 12 ID → Live2D/VRM. Не раньше, чем голос стабилен.

Не начинать с «дообучения на своих диалогах» и не начинать с 64 тегов. Сначала гомеостаз, потом обучение.

## Главный принцип

Fish-теги — это **мышцы лица голоса**.  
PAD + bond + память — это **нервная система**.  
LLM — **рот**.

Если рот сам назначает мышцы, получится маска. Если нервная система считает состояние, а рот говорит из него — получится персонаж, который по-разному встретит Папу, Настю и случайного человека в Discord, и вздрогнет, когда из памяти всплывет старый вечер.

Если дальше внедрять — логичный первый патч: санитайзер + `AffectRenderer` на 12 тегов без LLM. Это единственное изменение, которое сразу слышно в колонках.

## 1. Проблемы текущей архитектуры

### 1.1. Критично — санитайзер физически убивает теги эмоций
`Nira.clean_phrase_for_tts()` вырезает:
- любые скобочные конструкции (`\([^)]*REQUEST[^)]*\)` и, судя по описанию, скобки вообще),
- звёздочки действий (`*смеется*`),
- эмодзи и смайлы.

Fish Audio S2 / S2.1-Pro управляется именно тегами в `[квадратных скобках]` — `[радостно]`, `[шёпотом]`, `[очень взволнованно]`. Если санитайзер продолжит вырезать всё, что похоже на скобки, теги эмоций никогда не долетят до TTS. Это единственная точка кода, которую обязательно нужно переписать: она должна **пропускать** валидные `[emotion-tag]`-конструкции и вырезать только `REQUEST:`-мета-теги, эмодзи и текстовые смайлы. Отдельно стоит решить, что делать со звёздочками действий (`*смеется*`) — сейчас это просто теряемый сигнал, а его можно конвертировать в тег `[смеется]` вместо удаления.

Похожая проблема в `ChatMessage.__init__` (санитайзинг истории) — он тоже режет "незакрытые скобки". Нужно явно развести два разных текста реплики: (а) текст для TTS (с тегами), (б) текст для истории диалога/дашборда (без тегов, чтобы не засорять контекст LLM визуальным шумом и не путать модель, заставляя её при взгляде в историю думать, что скобки — это часть стиля речи).

### 1.2. Инструкции прямо запрещают то, что нужно для эмоций
`instruction.md`, по описанию, содержит "запрет эмодзи и смайлов" и "запрет markdown/звездочек" одним пунктом. Если туда же неявно попадают квадратные скобки — LLM будет натренирован промптом не генерировать теги вообще. Нужно точечно разрешить один конкретный синтаксис (`[tag]` в начале предложения) и явно запретить всё остальное (эмодзи, markdown, смайлы, действия в звёздочках как отдельный вид текста).

### 1.3. Эмоции нигде не существуют как состояние — только как результат генерации
Сейчас "эмоциональность" Ниры — это то, что LLM выведет исходя из `character.md` и истории диалога здесь и сейчас. Нет:
- явной переменной состояния (эмоция как число/вектор, а не как текст в контексте),
- затухания эмоции во времени (decay),
- переноса эмоции между репликами внутри одного разговора,
- переноса настроения между сессиями (у `Prompter` есть `clear_history()`, но нет "текущего настроения", которое переживает переинициализацию контекста).

Из-за этого модель не может "быть немного всё ещё раздражённой" после того, как тема разговора уже сменилась — каждая генерация практически заново решает, какую эмоцию показать, опираясь только на последние реплики.

### 1.4. Нет входного восприятия эмоций собеседника
Пайплайн STT → Voice Turn Buffering → Prompter → LLM нигде не анализирует **тон/эмоцию входящей реплики человека** отдельно от её текста. LLM, конечно, может это оценить сама по тексту, но explicit-сигнала (например, "пользователь звучит раздражённо") в промпт не прокидывается, и нет отдельного OpRole для этого — хотя архитектура `OperationManager`/`OpRoles` уже спроектирована как раз для подключения таких плагинов (STT, T2T, TTS, FILTER_TEXT, FILTER_AUDIO).

### 1.5. `known_users.json` — только идентификация, не отношения
Файл хранит ID, имена, алиасы. Для того, что ты просишь ("живо реагировать на разных знакомых и незнакомых людей") этого недостаточно — нужна ось "насколько Нира доверяет/привыкла/близка" с этим конкретным человеком, которая должна модулировать её эмоциональные реакции (с Создателем — шире диапазон эмоций и открытость, с незнакомым голосом в Discord — настороженность, меньше тепла, больше любопытства/неопределённости, пока не наберётся история взаимодействий).

### 1.6. Память не размечена эмоционально
`EpisodicStore`/`SemanticStore`/`VectorRetrieval`/`RecencyRetrieval` работают с фактами и временем, но не хранят "с какой эмоцией это запомнилось" и не взвешивают воспоминания по эмоциональной значимости при извлечении. Без этого невозможна "живая реакция на воспоминания" — у человека сильные по valence/arousal воспоминания всплывают легче и влияют на текущее настроение (mood-congruent recall), а сейчас `MemorySummarizer` просто выжимает суть без эмоциональной метки.

### 1.7. Нет единого места, куда "стекается" эмоция для промпта
`get_sys_prompt()` собирает статичные блоки (`instruction.md`, `character.md`, сцена, список участников Discord). Динамического блока "текущее эмоциональное состояние Ниры" там нет — а именно через такой блок LLM узнавала бы, что показывать голосом прямо сейчас.

## 2. Ландшафт на сентябрь 2026

### 2.1. Fish Audio: актуальный синтаксис тегов (важно — у тебя, скорее всего, S2 / S2.1-Pro, а не устаревший S1)
- **S1** (старая модель): фиксированный набор тегов в `(круглых скобках)`, только в начале предложения, английские названия эмоций.
- **S2 / S2.1-Pro** (актуальные): `[квадратные скобки]`, **свободный текст**, а не фиксированный словарь — можно писать `[радостно]`, `[очень взволнованно]`, `[шёпотом, немного грустно]`. Более 15 000 подтверждённых тегов, но по факту работает любое описание, которое понял бы актёр озвучки.
- Официальная документация Fish Audio прямо подтверждает: теги работают **на всех поддерживаемых языках, включая русский**, и рекомендует ставить тег в начало предложения. Русскоязычные интеграторы Fish Audio (агрегаторы вроде fish-audio.ru, aihere.ru) на практике используют именно русские теги — `[радостно]`, `[грустно]`, `[шёпотом]`, `[смеётся]` — и подтверждают, что модель их распознаёт наравне с английскими.
- Можно комбинировать/накладывать теги: `[sad][whispering]`, но сама Fish Audio советует **не стакать конфликтующие эмоции** и **перевыставлять тег только когда чувство реально меняется**, а не на каждое предложение подряд одинаково.
- Есть модификаторы интенсивности как свободный текст: `[слегка грустно]`, `[очень радостно]` — то есть интенсивность не отдельный параметр API, а часть текста тега.
- Отдельно от эмоций — паралингвистика: `[пауза]`, `[вздох]`, `[смех]`, `[шёпотом]`, `[emphasis]` перед словом для смыслового ударения.

### 2.2. Как индустрия в 2026 строит "эмоциональный движок" для AI-компаньонов/VTuber'ов
Ключевой паттерн, который сейчас считается более надёжным, чем "эмоция целиком из промпта" — **вынести эмоцию из LLM во внешнее детерминированное состояние**, а не полагаться на то, что модель "вживую" помнит, что она чувствовала 5 реплик назад (у трансформеров эмоция — это контекстно-зависимая проекция, а не хранимая переменная; она не имеет инерции сама по себе, если её явно не сохранять снаружи).

Практическая реализация этого паттерна (пример — открытый проект `affectus`, построенный на колесе эмоций Плутчика):
- эмоция хранится как вектор из 8 осей с интенсивностью (0..1) каждая: радость, доверие, страх, удивление, грусть, отвращение, гнев, предвкушение;
- есть команда "получить вектор", "добавить дельту к вектору", "применить затухание по времени" (`tick`);
- сам модуль не решает, что значит "радость" — это остаётся на откуп LLM/личности персонажа, модуль только хранит структуру и следит за релевантностью (соседние оси на колесе образуют смешанные эмоции: радость+доверие → любовь и т.п.);
- в контролируемом эксперименте (Claude Sonnet как движок диалога) такое внешнее состояние действительно давало "инерцию" настроения — после резкой смены темы разговора (позитив → внезапно негативная новость) агент с внешним эмоциональным состоянием давал более смешанный/переходный эмоциональный ответ вместо мгновенного переключения, то есть вёл себя более по-человечески.

Похожий паттерн в компаньон-приложениях (например, обсуждение архитектуры MoeChat) — весовой "mood_bonus", который усиливает эффект новых сообщений в зависимости от текущего настроения (если персонаж уже грустный — грустные сообщения "бьют сильнее"), и эмоциональная разметка сохраняемых воспоминаний.

### 2.3. Русскоязычные модели для оценки эмоции входящего текста (если понадобится отдельный классификатор)
Если захочешь не полагаться только на "LLM сама поймёт тон", есть лёгкие модели, дообученные на русском:
- **CEDR** (Corpus for Emotion Detection in Russian) — датасет и модели на его основе классифицируют радость/грусть/удивление/страх/гнев/отсутствие эмоции — набор эмоций почти один в один совпадает с базовыми осями Плутчика, что удобно.
- **rubert-tiny2**-модели, дообученные на эмоциях (агрессия/тревожность/сарказм/позитив/нейтральность) — маленькие (десятки МБ), гоняются на CPU почти бесплатно.
- Dostoevsky и подобные rubert-sentiment модели — грубая тональность (позитив/негатив/нейтрально), если нужен самый дешёвый вариант.

Такая модель — не обязательный компонент на старте, но хорошее дополнение позже (см. Фазу 5 плана ниже), потому что она даёт независимый от LLM сигнал "как реально прозвучала реплика человека", а не то, что LLM додумает по тексту постфактум.

## 3. Предлагаемая архитектура: "Nira Affect Core"

### 3.1. Базовые эмоции — рекомендация
Взять **8 осей Плутчика** как внутреннее представление (не как то, что видит пользователь напрямую):

`радость, доверие, страх, удивление, грусть, отвращение, гнев, предвкушение`

Почему именно они, а не Ekman-6 или чистый PAD:
- они естественно комбинируются в смешанные эмоции (радость+доверие → нежность/любовь, страх+удивление → тревога, гнев+отвращение → презрение и т.д.) — это даёт богатый выход даже с простым вектором;
- у них есть структура противоположностей (радость↔грусть, доверие↔отвращение, страх↔гнев, удивление↔предвкушение) — удобно для правил "нельзя расти обеим противоположным осям одновременно";
- они почти дословно пересекаются с категориями русскоязычных датасетов эмоций (CEDR), так что при желании подключить внешний классификатор для входного текста — маппинг тривиален;
- из 8 базовых осей легко считать производную пару **valence/arousal** (грубо: valence = радость+доверие+предвкушение − грусть−страх−отвращение−гнев; arousal = удивление+страх+гнев+радость − спокойные оси) — а valence/arousal напрямую управляют тем, *как* Fish Audio должен произносить фразу (громче/тише, быстрее/медленнее), даже если конкретный тег не подобран.

### 3.2. Новый модуль `src/emotion/` (по аналогии с уже существующим `src/memory/`)

```
src/emotion/
  state.py          # EmotionState — 8-осевой вектор + производные (valence/arousal)
  appraisal.py       # вычисление дельт по новому событию (речь юзера / собственный ответ)
  decay.py           # EmotionTicker — фоновая задача затухания по времени
  relationships.py    # доверие/близость к конкретному собеседнику (расширение known_users.json)
  tag_mapper.py       # EmotionState -> строка тега(ов) для Fish Audio
```

**`state.py` — пример структуры:**
```python
class EmotionState:
    axes: Dict[str, float]  # joy, trust, fear, surprise, sadness, disgust, anger, anticipation
    per_speaker_bias: Dict[str, Dict[str, float]]  # модификатор на конкретного человека
    last_update_ts: float

    def apply_delta(self, delta: Dict[str, float], speaker: str | None = None): ...
    def tick(self, dt_seconds: float): ...       # затухание, у каждой оси свой half-life
    def valence(self) -> float: ...
    def arousal(self) -> float: ...
```

Разным осям — разное время затухания: удивление гаснет за секунды-минуты, обида/гнев может держаться часами, а базовое "доверие" к человеку меняется медленно и почти не затухает само по себе (это уже про `relationships.py`, не про `state.py`).

### 3.3. Откуда берутся дельты (appraisal)
Два источника, оба реализуемы без новых тяжёлых моделей на старте:

**A. Дёшево и элегантно — переиспользовать уже существующий механизм `REQUEST:`-мета-тегов.**
В `response_pipeline()` уже есть Early-Stop-парсинг спецтегов из потока токенов LLM. Добавляем LLM-инструкцию генерировать в начале ответа скрытый мета-тег вида:
```
EMOTION_DELTA: {"joy": 0.2, "trust": 0.1, "surprise": -0.05}
```
Он вырезается тем же early-stop механизмом, что и `REQUEST:`, не долетает ни до истории, ни до TTS, и обновляет `EmotionState` до того, как начнётся синтез оставшегося текста. Никакой дополнительной модели, никакой лишней задержки — используется то, что уже есть в пайплайне.

**B. Точнее, но дороже — отдельный классификатор входа.**
Лёгкая ruBERT-модель (CEDR-based, ONNX, CPU) анализирует **распознанный текст пользователя** сразу после STT, до сборки промпта, и даёт независимую оценку тона реплики. Её выход подмешивается как ещё один источник дельты (с меньшим весом, чем "самоотчёт" LLM) — полезно как защита от того, что модель неправильно проинтерпретирует сарказм/раздражение через текст. На твоём железе (Ryzen 7 5700X3D) это исполняется на CPU за миллисекунды и не конкурирует с GPU-нагрузкой Whisper/LLM/TTS.

### 3.4. Как эмоция попадает в промпт
В `Prompter.get_sys_prompt()` добавляется новый динамический блок (по образцу уже существующего блока с участниками Discord):
```
### Nira's Current Emotional State ###
joy=0.72 trust=0.55 surprise=0.10 sadness=0.0 fear=0.05 anger=0.0 disgust=0.0 anticipation=0.30
Валентность: положительная (0.68). Возбуждение: среднее (0.35).
С этим собеседником (Вова/Создатель): высокое доверие, тёплая близость.
```
Плюс явное правило в `instruction.md`:
- один тег в начале каждого смыслового предложения, отражающий текущее эмоциональное состояние;
- разрешён свободный текст на русском внутри `[]`, включая модификаторы интенсивности (`[слегка]`, `[очень]`);
- запрещено стакать противоречащие теги (`[радостно][грустно]` одновременно);
- перевыставлять тег только когда эмоция реально сдвигается, а не дублировать на каждом предложении одно и то же (снижает "шум" и больше похоже на живую речь) — это прямая рекомендация из документации Fish Audio.

### 3.5. `tag_mapper.py` — логика перевода вектора в тег
1. Взять 1–2 оси с наибольшей интенсивностью выше порога (например, 0.3).
2. Интенсивность → модификатор: `<0.4` — без модификатора или "слегка", `0.4–0.7` — базовый тег, `>0.7` — "очень"/"сильно".
3. Собрать строку: `[очень радостно]` или, при двух осях, `[тепло][слегка взволнованно]`.
4. Персональный "идиолект" Ниры может переопределять типовые сочетания — например, если у неё в `character.md` прописан сарказм как черта характера, то сочетание disgust+joy маппится не в дословный перевод, а в `[саркастично]`.

Технически эту логику может выполнять как код (детерминированно), так и сама LLM (получив на вход блок состояния и having инструкцию сформулировать тег естественным языком) — второе гибче и естественнее по звучанию, первое — предсказуемее. Разумный компромисс: код считает "что доминирует", а LLM формулирует конкретную русскую фразу тега.

### 3.6. Личности и знакомство — `relationships.py` + расширение `known_users.json`
```json
{
  "discord_id": "...",
  "system_name": "Вова",
  "display_name": "Папа, Создатель",
  "aliases": ["Вова", "Папа"],
  "relationship": {
    "trust": 0.95,
    "familiarity": 1.0,
    "affinity": 0.9,
    "known_since": "2025-01-01",
    "baseline_bias": {"joy": 0.1, "trust": 0.2}
  }
}
```
Для незнакомого голоса/пользователя Discord создаётся временная запись с `familiarity: 0.0` и смещённым базовым состоянием (выше `surprise`/`anticipation`, ниже потолок `joy`/`trust` — настороженное любопытство вместо открытости). `familiarity` и `trust` растут небольшими, инкрементальными шагами при позитивных взаимодействиях (управляется тем же appraisal-механизмом — часть дельты идёт не в общий `EmotionState`, а в `per_speaker` профиль).

### 3.7. Память с эмоциональной меткой
`EpisodicStore.save()` при сохранении реплики дополнительно пишет снимок `EmotionState` на момент записи. `MemorySummarizer` при ночной консолидации сохраняет не только суть, но и доминирующую эмоцию воспоминания. `VectorRetrieval`/`RecencyRetrieval` получают третий фактор скоринга — эмоциональную релевантность (совпадение текущего настроения с настроением воспоминания usil "mood-congruent recall", либо просто высокий by-default вес для сильных по интенсивности воспоминаний, независимо от давности — так тревожные/радостные события "всплывают" ярче, как у человека).

### 3.8. Фоновое затухание
`Nira.start()` уже поднимает несколько фоновых процессов — по этому же паттерну добавляется `EmotionTicker` как ещё одна фоновая asyncio-задача, которая раз в N секунд вызывает `EmotionState.tick(dt)` и, при желании, транслирует обновлённое состояние в WebSocket-шину (`emotion_update` рядом с уже существующими `job_start`/`stt_status` и т.п.) — тогда `nira-web` дашборд сможет рисовать эмоцию в реальном времени, вплоть до колеса Плутчика с затухающими секторами, как в примере с `affectus viz`.

## 5. На что обратить внимание, чтобы не сломать характер
- Без порогов и капов легко получить "эмоциональные качели" — гнев одной резкой репликой пользователя не должен взлетать до максимума за один шаг; дельты должны быть маленькими, а не абсолютными присвоениями.
- Стоит держать "личностный якорь" — базовый вектор, к которому состояние медленно возвращается в состоянии покоя (у каждого персонажа свой темперамент: у Ниры, например, можно сделать базовый лёгкий перекос в `trust`/`anticipation`, если по `character.md` она любопытная и доверчивая к Создателю).
- Тег на каждое предложение подряд быстро начинает звучать неестественно и вырос ценой лишних токенов — используйте правило "перевыставлять только при сдвиге", а не всегда.
