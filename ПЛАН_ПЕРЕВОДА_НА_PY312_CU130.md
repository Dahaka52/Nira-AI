## 2. Внешние ограничения и факты (на 2026-03-05)

- PyTorch официально публикует `cu130` wheel для `torch/torchaudio/torchvision` (включая `cp312` и `win_amd64`).
- `flash-attn` в официальном репозитории ориентирован на Linux; Windows отмечен как экспериментальный путь.
- В форке `apps/Qwen3-TTS-streaming-main` для Windows используется сторонний prebuilt wheel `flash_attn ... cp312 ... win_amd64` + `triton-windows`.
- ONNX Runtime: стабильный `onnxruntime-gpu` на PyPI ориентирован на CUDA 12.x; CUDA 13.x указан как nightly-канал.

## 3. Конфликты и решения

| Конфликт | Критичность | Что ломается | Решение |
|---|---|---|---|
| `transformers==4.52.4` (core) vs `qwen-tts` (`4.57.3`) | Высокая | Нельзя безболезненно обновить в одном env при наличии legacy-компонентов | Разделить профили: `core` и `qwen` (рекомендуется), либо принять апгрейд до `4.57.3` и убрать несовместимые TTS-модули |
| `fugashi==1.3.0` | Высокая | Нет `cp312 win_amd64` wheel для этого пина | Поднять до версии с wheel под cp312 (например `1.5.2`) |
| `mkl-service==2.4.0` | Высокая | Нет wheel для cp312 | Поднять до `2.6.1+` |
| `rvc==0.3.5` + `fairseq` | Критическая (для RVC) | `fairseq` не имеет готовой поддержки под такой стек; у `rvc` также строгие старые зависимости | Вынести `rvc` в отдельный legacy env (`py310/cu128`) или временно отключить `rvc` в новом окружении |
| `flash-attn` на Windows | Высокая | Официального простого пути нет, возможны ABI/torch mismatch | Использовать только wheel, собранный под точную связку (`cp312 + cu130 + torch2.10`), держать fallback на SDPA |
| `onnxruntime-gpu` и CUDA 13 | Средняя/Высокая | При GPU-режиме STT возможны несовместимости с CUDA 13 stable stack | Для STT держать `provider: cpu` на этапе миграции; GPU-режим тестировать отдельно (при необходимости nightly ORT CUDA13) |
| Подмешивание user-site пакетов | Высокая | Непредсказуемые версии в рантайме | Запускать с `PYTHONNOUSERSITE=1`, создавать полностью чистое env |
| Hardcode пути `.conda` в `start_nira.ps1` | Средняя | Нельзя прозрачно переключать старое/новое env | Параметризовать путь окружения (`NIRA_CONDA_PREFIX` или аргумент) |

## 4. Целевая стратегия миграции

Рекомендуемый путь: **двухфазная миграция с минимальным риском**.

1. Перевести **core** проекта на `py312 + cu130` в новом conda-префиксе.
2. Подключить `flash-attn` (Windows prebuilt) и валидировать Qwen-контур отдельно.
3. `rvc` оставить вне нового env (или отдельный legacy env), пока не будет подтвержден рабочий стек без `fairseq`-блокеров.

## 5. Поэтапный план работ

## Этап 0. Freeze и backup

1. Зафиксировать текущее состояние:
   - `conda list -p .\.conda > docs/env/conda-list-2026-03-05.txt`
   - `.\.conda\python.exe -m pip freeze > docs/env/pip-freeze-2026-03-05.txt`
2. Сохранить рабочие конфиги (`configs/config.yaml`, `.env`).
3. Не удалять старую `.conda` до завершения acceptance.

## Этап 1. Создание нового conda окружения

1. Создать новый префикс:
   - `conda create -y -p .\.conda312 python=3.12 pip`
2. Активировать и проверить:
   - `conda activate .\.conda312`
   - `python -V` (должно быть `3.12.x`)
3. Включить изоляцию:
   - `set PYTHONNOUSERSITE=1` (и зафиксировать в запускных скриптах).

## Этап 2. Базовый CUDA/PyTorch стек

1. Установить PyTorch под `cu130`:
   - `pip install torch==2.10.0 torchvision==0.25.0 torchaudio==2.10.0 --index-url https://download.pytorch.org/whl/cu130`
2. Smoke-проверка:
   - `python -c "import torch; print(torch.__version__, torch.version.cuda, torch.cuda.is_available())"`

## Этап 3. Flash-attn + Triton (Windows)

1. Ставить только wheel под точную ABI-связку:
   - `flash_attn-2.8.3+cu130torch2.10-cp312-cp312-win_amd64.whl`
2. Установить `triton-windows` (зафиксировать рабочую версию, например ветка `<3.7`).
3. Проверить импорт:
   - `python -c "import flash_attn; print('ok')"`
4. Если импорт/инференс нестабилен:
   - fallback на SDPA (`attn_implementation=sdpa`) без остановки миграции core.

## Этап 4. Рефактор зависимостей проекта под py312

1. Разделить зависимости на профили:
   - `requirements-core.txt` (без `rvc/fairseq`-цепочки),
   - `requirements-qwen.txt` (Qwen/flash-attn),
   - `requirements-legacy-rvc.txt` (если нужен отдельный env).
2. Обязательные коррекции пинов:
   - `fugashi: 1.3.0 -> 1.5.2+`
   - `mkl-service: 2.4.0 -> 2.6.1+`
3. Удалить или вынести в optional все, что тянет `fairseq` в main env.
4. После установки прогнать:
   - `pip check` (в новом env должен быть чистый или с заранее принятыми исключениями).

## Этап 5. Адаптация скриптов запуска и документации

1. Обновить `start_nira.ps1`:
   - убрать жесткую привязку к `.conda`,
   - добавить параметр/переменную окружения пути к env,
   - выставлять `PYTHONNOUSERSITE=1`.
2. Обновить `README.md`:
   - убрать конфликт `cu128` vs `cu130`,
   - удалить/заменить шаг `python install.py`,
   - явно описать профили установки (`core`, `qwen`, `legacy-rvc`).

## Этап 6. Функциональная валидация

1. Базовые проверки:
   - запуск backend через новый env,
   - `/api` доступен,
   - STT (`sherpa`) в `provider: cpu` работает стабильно,
   - T2T (`llamacpp`) работает.
2. Qwen/flash-attn проверки:
   - smoke генерация аудио,
   - проверка first-chunk latency и отсутствия падений.
3. Зафиксировать результаты в `docs/env/migration-report-2026-03-05.md`.

## Этап 7. Cutover и rollback

1. Cutover:
   - переключить запускные скрипты на новый env.
2. Rollback:
   - вернуть путь env на старую `.conda`,
   - перезапустить backend,
   - использовать старый config-профиль.

## 6. Критерии готовности (DoD)

- Backend стабильно стартует на `Python 3.12`.
- `torch` работает с `cu130` (`torch.cuda.is_available() == True`).
- `flash-attn` импортируется и используется в целевом Qwen сценарии (или документирован fallback SDPA).
- `pip check` в новом env без критических конфликтов.
- Скрипты запуска не завязаны на один жесткий путь окружения.
- README и dev-инструкции соответствуют фактическому процессу установки.
