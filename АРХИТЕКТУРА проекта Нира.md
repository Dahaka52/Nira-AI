# Архитектура проекта "Нира" (Техническая спецификация)

Данный документ описывает полное устройство проекта, включая программные абстракции (классы, методы), пайплайны данных, конфигурации запуска и взаимодействие компонентов. Это техническая база для дальнейшей разработки и интеграции.

## 1. Концепция и Пайплайн (High-Level Overview)

Nira — это асинхронный backend для AI-персонажа. Он построен на принципах модульности и очереди задач (Job Queue).
Основной пайплайн:
`Аудио ввод (Микрофон/Discord)` ➔ `VAD (Voice Activity Detection)` ➔ `STT (Speech-to-Text)` ➔ `Обновление контекста` ➔ `T2T (LLM)` ➔ `Text Filters` ➔ `TTS (Text-to-Speech)` ➔ `Audio Filters` ➔ `Вывод аудио`.

Вся архитектура поддерживает **потоковую обработку (streaming)**. Данные передаются чанками через асинхронные генераторы (`async for chunk in operation`).

---

## 2. Ядро Системы: Класс `JAIson`

**Файл:** `src/utils/jaison.py`  
Класс `JAIson` является главным оркестратором (Application Layer). 

**Зона ответственности:**
- **Job Queue (Очередь задач):** Обрабатывает задачи последовательно через корутины. Если генерируется ответ (`response`), остальные задачи ждут. Отмена задач реализована через безопасную очистку корутин.
- **Immediate STT-path:** Отдельный внеочередной путь для быстрого голосового ввода (`process_audio_immediate()`), который может перебивать текущую генерацию (barge-in/interrupt).
- **Событийная шина (Event Server):** Транслирует изменения по WebSocket (например, когда LLM начинает писать текст).

**Ключевые методы `JAIson`:**
- `create_job(job_type, **kwargs)` — ставит задачу в очередь (например, генерацию ответа).
- `submit_audio_immediate(payload)` — быстрая обработка аудио вне очереди с поддержкой backpressure (защита от перегрузки).
- `process_audio_immediate(audio_bytes, ...)` — парсинг STT и принятие решений (перебить ли нейросеть, если сказано слово-триггер).
- `append_conversation_context_text(...)` — запись в историю диалога перед вызовом LLM.
- `response_pipeline()` — полный цикл генерации ответа: извлечение истории ➔ LLM ➔ Фильтры ➔ TTS.

## 3. Модули (Operations) и их Контракты

Все вычислительные блоки (STT, T2T, TTS, Filters) реализованы как независимые модули-наследники базового класса `Operation` (`src/utils/operations/...`). Управление ими осуществляет `OperationManager`.

### Контракт класса `Operation`
Любой модуль обязан реализовывать:
- `configure(config_dict)` — инициализация параметров из `config.yaml`.
- `get_configuration()` — отдача текущих настроек.
- `_parse_chunk(chunk)` — обработка входящего кусочка данных (текста или аудио).
- `_generate(payload)` — асинхронный генератор результата (`yield chunk`).

### 3.1. STT (Speech-to-Text)
**Файлы:** `src/utils/operations/stt/...`
Поддерживает несколько провайдеров. Активный STT выбирается в `configs/config.yaml` параметром `stt_active_id`.
- `FasterWhisperSTT` — `faster_whisper_ru` (CUDA, инференс на RTX 5070).
- `OpenAISTT` — API совместимое с Groq (`groq_stt`).
- `GoogleLiveSTT` — потоковый STT от Gemini.
- `SherpaSTT` — обертка для взаимодействия с `stt-sherpa-server`.

**Контракт STT V2:**
Вход: `audio_bytes`, `sr`, `sw`, `ch`.
Выход: dict с `text`, `is_final`, `confidence`, `stt_latency_ms`.

### 3.2. T2T (Text-to-Text / LLM)
Генерирует ответы на основе промптов (`prompter`). Основной движок для локальной работы: `llamacpp`.
- Под капотом `JAIson` запускает `llama-server.exe` как дочерний процесс.
- Использует флаг `--flash-attn on` и архитектурные оптимизации под `sm_120` (RTX 5000 серия, CUDA 13.0).

### 3.3. TTS (Text-to-Speech)
Отвечает за синтез речи из текстовых чанков. На данный момент настроен `fish_audio` (облако). В архитектуре заложен фундамент для `MeloTTS` в качестве плагина.
**Контракт TTS:** 
Вход: `{ "content": "текст", "emotion": "опционально" }`
Выход: `{ "audio_bytes": "bytes", "sr": 24000, "sw": 2, "ch": 1 }` (стримингом, не блокируя event loop).

### 3.4. Текстовые и Аудио фильтры
Запускаются цепью. 
- `filter_text`: `filter_clean` (чистка артефактов), `chunker_sentence` (нарезка на предложения для TTS), `emotion_roberta` (определение эмоций через ML `SamLowe/roberta-base-go_emotions`).
- `filter_audio`: `pitch` (тонгенератор), `rvc` (изменение голоса на базе моделей RVC).

## 4. Исполняемые файлы и Клиенты (Apps / Bin)

### 4.1. Главные точки входа (Entrypoints)
- **`src/main.py`** — запускает `JAIson` и Web-сервер (`src/utils/server.py`) под управлением `Quart`.
- **`src/cli.py`** — консольный клиент. Инициализирует `JAIson` локально и использует `ConsoleChatObserver` для прослушивания WebSocket-событий (выводит текст побуквенно в терминал).
- **Скрипты запуска:** `start_nira.bat` / `start_nira.ps1` (настраивают переменные окружения, активируют Conda и запускают `main.py`).

### 4.2. Автономные приложения (Клиенты)
Эти модули живут в папке `apps/` и общаются с ядром по сети:
- **`hw-mic-client`:** Умный клиент микрофона на базе `sounddevice`. Реализует VAD (Voice Activity Detection), RMS (анализ громкости), Soft limiter и AGC (Auto Gain Control). При обнаружении голоса шлет запрос `POST /api/context/conversation/speech_start` (чтобы нейросеть замолчала), а затем шлет аудио-чанки в `POST /api/context/conversation/audio`.
- **`discord-bridge`:** Бот на базе `py-cord`. Заходит в голосовые каналы, слушает пользователей и пробрасывает аудио в ядро Nira. Поддерживает DAVE/E2EE шифрование.
- **`nira-web`:** React/Vue UI для визуализации мыслей Ниры, истории и задержек (metrics: `tps`, `ttft_ms`).

### 4.3. Управление фоновыми процессами (Sidecars)
Некоторые инструменты (например, `llama-server.exe` или `sherpa-onnx`) работают как отдельные бинарники. 
**Класс `STTProcessRunner`** (в `src/utils/processes/...`) управляет их жизненным циклом:
- `ensure_running()` — стартует процесс из конфига (например, `process_autostart: true`).
- `health()` / `ensure_healthy()` — пингует локальный порт процесса.
- `restart()` — перезапускает процесс при зависании или краше.

## 5. Долговременная память (`src/memory`)
Архитектура памяти разделена на 4 функциональных блока, каждый со своим классом и зоной ответственности:
1. **`store`:** Векторная база данных. Хранит факты, эмбеддинги и референсы (вероятно на базе ChromaDB/FAISS или SQLite).
2. **`retrieval`:** Логика поиска по памяти (Similarity Search). Вызывается перед формированием контекста в `response_pipeline()`.
3. **`consolidation`:** Фоновый процесс "осмысления". Проходится по недавним логам диалогов и сжимает их в "опыт" (суммаризация фактов, сброс мусора).
4. **`identity`:** Ядро личности. Обновляет промпты персонажа (`prompter.character_prompt`), добавляя новые черты характера или эмоции, основанные на консолидированном опыте.

## 6. Интерфейсы взаимодействия (Способы связи)

### 6.1. REST API (`src/utils/server.py`)
Определяет endpoints (маршруты) для управления системой. Спецификация OpenAPI 3.1.0 лежит в `api.yaml`.
- **Контекст:** `POST /api/context/conversation/text`, `POST /api/context/conversation/audio`, `DELETE /api/context`.
- **Очередь:** `POST /api/response` (создать задачу генерации ответа).
- **Управление модулями:** `POST /api/operations/reload`, `POST /api/operations/use`.
- **Система:** `GET /api/pipeline` (информация об очереди `queue_size` и статусе процессов).

### 6.2. WebSockets (Реальное время)
Используется для подписки на события JAIson. Класс `BaseObserverClient` (в `src/utils/helpers/observer.py`) позволяет клиентам слушать события.
События строго типизированы (класс `JobType`):
- `job_start`, `job_finish`, `job_cancelled`.
- Во время `response` прилетают события: `result.instruction_prompt` ➔ `result.history` ➔ `result.content` (стриминг чанков текста) ➔ `result.audio` (стриминг аудио чанков).

## 7. Конфигурация и окружение

- **Окружение:** `setup_env_py312_cu130.ps1` разворачивает Python 3.12, PyTorch под CUDA 13.0, Flash-Attention wheel и Triton.
- **Главный конфиг:** `configs/config.yaml`.
  Здесь определяется:
  - Какие модули включены (`stt_active_id`, `t2t_active_id`).
  - Параметры генерации (`temperature`, `top_p`, `max_length`).
  - Пути до моделей (`llamacpp_model_filepath`).
  - Тонкие настройки VAD микрофона (`vad_threshold`, `voice_merge_window_ms`).
  - Настройки Промптера (файлы с характером, инструкциями и сценами из папки `prompts/`).

## 8. Итог

Архитектура строго разделена на:
1. **Тяжелые вычислители (Sidecars/API):** `llama-server`, облака (Groq, FishAudio), `sherpa-onnx`.
2. **Асинхронный мозг (JAIson):** Управляет потоками, памятью, контекстом и задачами.
3. **Автономные клиенты (Mic/Discord/UI):** Только слушают и отправляют триггеры, не занимаясь логикой ответа.

Такое разделение позволяет Нире одновременно слушать звук, синтезировать речь, определять эмоции и параллельно обдумывать воспоминания (consolidation), не блокируя основной процесс.

## 9. План зачистки (Legacy & Useless)

В ходе архитектурного анализа были выявлены компоненты и рудименты, которые являются бесполезными или конфликтными для текущих целей проекта (локальный русскоязычный AI vTuber без цензуры на базе RTX 5070). От них рекомендуется избавиться для ускорения пайплайна и чистоты кода:

> [!WARNING]
> **Несовместимость с русским языком (Важно!)**
> Фильтр эмоций `emotion_roberta` (на базе `SamLowe/roberta-base-go_emotions`) обучен **только на английском языке**. Если Нира генерирует текст на русском, фильтр будет работать некорректно или выдавать шум. Требуется либо удаление, либо замена на мультиязычную модель (например, на базе `XLM-RoBERTa`).

> [!TIP]
> **Модуль модерации (`mod_koala`)**
> В архитектуре форка заложен фильтр модерации контента. Учитывая использование uncensored/NSFW модели `Katarau-9B-ru-RP-nsfw`, фильтр модерации будет лишь тратить процессорное время и конфликтовать с характером персонажа. Рекомендуется полностью исключить его из пайплайна.

> [!NOTE]
> **Облачные рудименты ядра JAIson**
> В коде `src/operations/` осталась избыточная логика для интеграции с Azure, OpenAI, AWS. Для полностью локальной системы (на базе llama.cpp / sherpa-onnx) этот код является мертвым грузом и усложняет поддержку.

> [!NOTE]
> **Legacy TTS и мусорные файлы**
> 1. В `README` и зависимостях упоминается легаси TTS стек (MeloTTS/RVC). Учитывая план по разработке нового TTS-плагина, старые зависимости (включая `requirements.legacy-tts.txt`) можно удалить.
> 2. Файлы `test_audio.wav`, `Nira_voice.wav`, скрипты `test_google_stt.py` и `_ARCHIVED_legacy_tts.txt` захламляют корневую директорию. Их следует перенести в папку `tests/` или `scratch/`.
